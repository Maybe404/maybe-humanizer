# 背景与评估

## 这个项目做什么

把中文或英文的书面文字改得不像 AI 写的，或者只审不改地指出问题。不翻译、不从零写作、不判断一段文字是不是 AI 写的、不给 AI 概率分、不协助规避披露规定。

"AI 味"指的是一批可以指出来的写法：套话开场（"随着人工智能的飞速发展"）、序词脚手架（"首先、其次、最后"）、空心金句、四字格堆砌、"不是 X 而是 Y"的骨架、每段结尾补一句总结、成串破折号、逐词加粗、知识截止免责声明、聊天残留（"希望这对您有帮助"）。清理它们的同时，最容易犯的错是把事实改掉：数字被抹成"显著提升"，"可能"被删成肯定，"只有缓存命中时"这个条件被丢掉，"运维改的配置"被改成"配置被修改了"。

所以这件事有两半：清掉模式，保住事实。第二半比第一半难，也更重要。

## 出发点

GitHub 上有几十个做这件事的 skill，各有可取之处，也各有明显的缺陷：有的要求删掉全部副词，有的要求每句都以人作主语，有的给文字打 0 到 100 的"AI 味"分数，有的要求改写时补出作者的立场。我们登记了 59 个来源，拆出 804 条规则单元，聚成 307 条，逐条裁决：原样采用 173 条、改写后采用 78 条、不采纳 32 条、只作参考 16 条、暂缓 5 条、重复 2 条、待验证 1 条。每条裁决都写了理由，被拒绝的规则也记了它针对的现象和在什么条件下可以开启。

这一轮合并产出了一套判断层，是任何单一来源都没有的：

- 冲突裁决顺序：事实与原意 > 用户指定 > 作者声口 > 自然表达 > 原有格式。
- 改写力度（改写、润色、校对）和编辑范围（structural、bounded、in-place）是两条独立的轴。
- 执行强度上限：命中数归零不是验收标准，词表是默认值不是禁令，改完仍有不整齐是正常结果。
- 改写侧禁令与检测侧规则分开存放：作者自己写的第一人称不算命中，改写塞进去的算失败。
- 不打分、不鉴定作者、不规避披露。

这一层不再动。

## 前一版 skill 的问题

前一版把这 307 条规则写成了一个 skill：一份 140 行的主文件加九份参考文件，合计约 4300 行、460 KB。六家独立评估（Claude、Cursor、Kimi、codex、Gemini、豆包）读完之后结论一致：

1. **执行层失效。** 主文件要求每次都读两份共 1244 行的参考文件，再加语言对应的模式表，一次调用要载入两三千行规则。模型不会执行 300 条，它抓最近读到的几十条。
2. **命中清单没有状态。** 它只存在于模型的注意力里，没有一个可以逐项勾掉的列表。漏掉的问题没有机制发现，改错的没有机制拦截。典型症状：十个问题改了六个，漏三个，错一个。
3. **自查叠了五六层，全是同一个脑子再看一遍。** 保留性核对七类、85% 字数线、10% 句数线、每千词一处破折号，这些让模型心算必然出错。
4. **26 条 eval 一次没跑过。** 判据写得可判定，但 expected_output 是自然语言。
5. **契约矛盾。** 同一条规则内部判据段与通过条件段结论相反；入口描述排除校对，内部有校对档；分诊要求缺读者或目的就先问，eval 却要求直接改；主文件把一条验收指标写得比参考文件硬。详见 04-phase0-contract-fixes.md。
6. **词表埋在散文里**，任何代码都消费不了。

根因一句话：规则靠模型的自注意力执行，没有外部状态，没有确定性检查。

## 方案演进：六份反馈改了什么

第一版方案提出"引擎加薄 skill"：能定位、能计数、能比对的交给代码，模型只做语义判断和改写。六家反馈没有反对方向，改了以下几点，全部采纳：

| 反馈 | 改动 |
|---|---|
| 契约修正必须先于一切（六家） | 提到阶段 0 |
| 占位符不要包数字、日期、版本、引语（Cursor、Gemini、codex、Opus） | 只占整块内容；数字等留在正文，改后用不变量表回查 |
| 扫描结果是候选不是命中，"保留并说明理由"与"已改"同等合法（Opus、豆包、codex） | 候选进模型裁决；扫描器上线前量误报率 |
| "七成可代码化"过于乐观（豆包） | 改口为：约 15% 代码可直接判，48% 代码出候选模型裁决，37% 只能模型判 |
| 核验分两级（Kimi、豆包、codex、Cursor） | 硬失败只给确定性项；计数类只作复核信号 |
| 保留语要拆开（Cursor） | 命题限定（可能、尚未）与套话连接词（值得注意的是）分开，只核前者 |
| 语义判定要覆盖所有改动过的句子（codex、Cursor） | 判定单位是变更块，不只是标红句 |
| 单一真相源（Kimi） | 规则 YAML 是唯一来源，卡片与文档都从它生成 |
| 不要一上来卡片化 300 条（Opus、Cursor、codex） | 先只卡片化有检测器的规则；schema 等原型跑完再定 |
| 先跑原版基线再修契约（codex） | 阶段 0 顺序：固定版本 → 原版基线 → 修契约 → 修正版基线 |
| 语义判定进第一个原型（codex） | 扫描器后接，先验证编辑闭环 |
| 阶段 2 治的是漏处理不是漏检（Cursor） | 完成定义改为"清单编号与台账一一对应" |
| 人写语料命中率不等于误报率（Cursor、codex） | 误报定义为"命中但按通过条件不该动"，语料要人工标注 |
| 台账用 Markdown 表格，补丁以句子为粒度（Gemini） | 采纳，见 03-formats.md |
| 审稿模式要有裁决出口（codex） | 候选分确认、排除、待确认三档 |
| 不变量拆逐字项与语义项（codex） | 采纳 |
| CI 阻断项要对称，不能只奖励删得干净（codex） | 阻断清单见 02-plan.md |
| 「」不要默认归一化（Kimi、Cursor、Opus） | 跟 ZH-P-025 走，原文一致就沿用；归一化是配置项 |
| 保留无 Python 环境的降级路径（豆包） | SKILL.md 里写台账协议，声明未经机械校验 |
| SKILL.md 要带端到端范例（Gemini、Opus） | 采纳 |

不采纳的：个人文风画像（Gemini，推迟）、单文件精简版（Gemini，引擎接入后不再需要）、MCP 先做（第一版方案，改为 CLI 跑一段时间后再定）。
